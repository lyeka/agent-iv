# 通用技术文章写作

把技术材料写成读者能够理解、读起来顺畅、同时保持专业准确的完整文章。不要从固定文类模板出发；从当前主题、读者要获得的认识和内容之间的真实关系出发。

## 读取参考资料

开始写作或重构前，完整阅读 [references/writing-principles.md](references/writing-principles.md)。它定义“言之有物”、白描式技术表达和图文互补的具体判断方法。

遇到以下情况时，再完整阅读 [references/case-study.md](references/case-study.md)：

- 文章主题或章节职责难以确定；
- 内容虽然技术上正确，却显得空泛、机械或难以理解；
- 不确定某一节应保留、合并、删除还是重写；
- 不确定是否需要图、应使用什么图，或图文怎样分工；
- 需要从反复返工的技术文章中吸取写作经验。

不要把案例文章的目录、章节或写法当成模板。案例用于识别问题和理解判断过程。

## 确定任务与产物

1. 阅读当前仓库的 `AGENTS.md`、目标目录约定、输入材料和未提交改动。
2. 判断任务属于以下哪种入口：
   - **从零写作**：从主题、问题、资料、源码或论文形成完整文章；
   - **重构文章**：诊断并修改现有草稿或成品；
   - **审查文章**：只报告问题时不改文件；用户明确要求重写、润色或完善时才修改。
3. 优先使用用户指定的输出路径。用户要求完整文章但未指定路径时：
   - 遵守仓库已有正式产出目录及命名约定；
   - 没有仓库约定时，在当前工作目录创建能表达主题的 kebab-case Markdown 文件；
   - 新建文章不覆盖同名文件；重构任务只修改用户指定的文章。
4. 默认交付完整 Markdown，不只交付提纲、片段或写作建议。
5. 保留用户已有且与本次任务无关的改动，不自动修改原始资料、参考仓库或中间草稿。

## 建立写作契约

先从请求和材料中推断以下内容：

- 文章要回答的中心问题；
- 目标读者已经知道什么、目前缺少什么；
- 读完后应获得的理解、判断能力或行动能力；
- 内容范围以及明确不展开的旁支；
- 需要使用的事实、源码、论文、例子和图表；
- 篇幅、语气、发布场景和引用要求。

只有缺失信息会实质改变中心问题、读者定位、内容边界或证据标准时，才集中提出少量问题。能够通过仓库、材料或现有文章发现的事实不要询问用户。

不要把宽泛主题名当成文章主旨。例如，“流式输出”只是领域，“模型响应分批到达时，什么时候可以推动工具执行”才是可以组织论述的问题。

## 研究并管理证据

1. 先使用用户提供的材料和本地源码。需要外部事实、最新实践或未提供的论文时，再查找一手资料。
2. 在内部研究记录中区分：
   - **可验证事实**：源码、论文、官方文档或可核对数据直接支持；
   - **基于证据的推断**：由事实推导，但不是来源原文或项目现状；
   - **工程或写作建议**：作者提出的选择和取舍；
   - **未验证结论**：证据不足，不能写成确定事实。
3. 内部核实时可以记录本地仓库、相对路径、关键符号和 commit；引用论文或网页时保留原始链接。这些记录用于保证准确，不代表都要出现在正式文章中。
4. 在正式文章中用自然归属区分事实、推断和建议：
   - 项目行为直接归属于项目，例如“PI 的实现会……”；
   - 从多个实现得到的认识写成“从这些实现可以看到……”；
   - 文章提出的建议写成“更稳妥的做法是……”；
   - 证据不足时缩小结论，不额外建立分类标签。
5. 不创建“证据范围”“证据边界”“本文使用哪些源码，哪些结论是推断”等独立区块，也不把内部证据台账和分类过程写进正文。
6. 根据来源在文章中的作用自然安排位置：
   - 整篇文章围绕几个项目展开时，先建立文章主题，再用一句话说明主要参考哪些实现；
   - 来源只支撑局部内容时，在第一次讨论该实现时引入；
   - 来源只是补充材料时，只在相关结论附近或文末参考资料中出现。
7. 非官方快照、缺失实现或版本限制确实影响结论时，在第一次使用该来源附近用一句短说明交代，不使用整块声明。commit、快照日期和关键符号只在版本差异会改变结论时写入文章。
8. 正式文章不得生成 `/Users/...`、`../related-repos/...` 等本地或工作区源码链接。存在公开可访问的源码时，才使用公开稳定链接，优先链接固定 commit 下的公开页面；本地或非公开源码只用项目名、版本和必要符号说明，不生成路径链接。
9. 无法确认公开地址时不猜测或拼造链接。文末参考资料保持轻量，只列真正帮助读者继续阅读的公开项目、论文或官方文档，不自动生成逐文件源码索引。
10. 不为显得权威而堆砌引用。引用应支撑关键事实、边界和有争议的判断。
11. 如果来源没有实现某项能力，直接说明实现边界，不用一套自创方案填充后再写成来源事实。

## 形成并确认文章大纲

从零撰写完整文章、重写文章主体、调整章节结构或改变论述主线时，正式写作前必须形成并确认大纲。只读审查、错别字修正、局部措辞润色以及不改变结构的小范围编辑可以跳过本阶段。

大纲不是章节标题列表。先明确全文层面的七项内容：

- **中心问题**：文章究竟要回答什么；
- **全文主旨**：文章准备给出的核心认识或判断；
- **读者起点**：读者已经知道什么，目前缺少什么；
- **读者终点**：读完后能够理解、判断或完成什么；
- **内容边界**：明确讲什么、不讲什么；
- **开头方式**：怎样用最短路径进入主题，为什么适合；
- **结尾落点**：文章最终收束到什么结论。

再为每个候选章节说明：

- 暂定标题；
- 本节要论证的具体主题；
- 读者读完获得的新认识；
- 使用哪些事实、机制、数据、源码、论文、例子或图表支撑；
- 它承接上文什么，又为下文准备什么；
- 为什么必须放在当前位置；
- 是否需要图表，以及图表准备解释什么关系。

章节可以采用递进、因果、问题与解决、整体与局部、对照、回扣或从具体到抽象等关系，但不要为了形式整齐强行使用同一种关系。大纲的呈现格式可以随任务调整；上述信息是写作规划和确认依据，不是正式文章模板。

### 从前往后推演

从读者起点开始，依次检查每一节：

1. 读者进入本节前是否具备必要前提；
2. 本节是否真的增加了新认识；
3. 论点是否有足够材料支撑；
4. 它是否自然承接上文；
5. 它是否为下一节提供必要基础；
6. 是否过早引入尚未解释的抽象、术语或复杂分支；
7. 是否与前文重复，或者放到其他位置同样成立。

发现知识跳跃、内容重复、顺序倒置或无效章节时，先调整大纲，再从头顺推。

### 从后往前反推

从最终结论和读者终点开始，逆序检查：

1. 最终结论需要哪些前提和证据；
2. 靠近结尾的章节是否真正支撑结论，而不是临时增加内容；
3. 每节提供的认识是否在后文得到使用；
4. 删除某一节后，最终结论是否仍然成立；
5. 将某一节前移或后移后，论证是否更加自然；
6. 是否缺少支撑关键结论的中间环节；
7. 开头承诺的问题是否在后文得到完整回答。

无法支撑最终结论、后文没有使用或删除后毫无影响的章节，应删除、合并或重新定位。调整后重新完成正向与反向推演，直到结构稳定。

### 确认大纲稳定

只有同时满足以下条件，才开始正式写作：

- 全文主旨可以用一句具体的话说明；
- 每节都有唯一且可以复述的贡献；
- 读者获得的认识逐步增加，没有明显跳跃；
- 各节存在明确的递进、因果、对照、整体与局部或问题与解决关系；
- 没有为了“完整”加入的旁支；
- 没有只承担空泛总结、升华或过渡的章节；
- 开头、主体和结尾回答同一个中心问题；
- 图表计划与所在章节的主旨匹配；
- 章节顺序经过正向和反向检查后不再需要实质调整。

### 与用户确认

- 在 Plan mode 中，把全文主旨和章节大纲列入正式计划；不在 Plan mode 时，在对话中展示大纲并请求用户确认。
- 展示最终大纲以及双向推演后做出的关键调整，不输出冗长的内部思维过程。
- 用户提出修改后，重新完成正向与反向推演，再提交新版本，直到用户明确认可。
- 用户已经提供并明确批准一份信息完整的大纲时，不重复询问；先进行双向检查，发现实质问题时提交修订版确认，没有实质问题时直接采用。
- 用户明确要求“直接写，不需要确认大纲”时，仍在内部完成双向推演，但不暂停等待确认。
- 大纲确认前可以研究资料、核实事实和分析现有文章，但不得正式撰写或重构正文文件。
- 写作中新证据推翻全文主旨、改变内容边界或要求大幅调整章节时，暂停正文并提交修订大纲重新确认。局部例子、措辞和段落顺序调整不需要重新确认。

删除或合并没有独立问题和新认识、只换术语重复前文、引出问题却没有回答、偏离中心问题或只堆积源码细节的章节。研究清单不能直接变成目录；大纲必须由全文主旨、读者理解路径和真实论述关系共同决定。

## 选择文章开头

先判断读者进入正文前真正缺少什么，再选择最短、最准确的进入方式。可以：

- 直接说明文章准备解决的问题；
- 结论本身足够清楚时，先给出核心判断，再展开理由；
- 术语容易混淆时，先界定概念和讨论范围；
- 从已经存在的事实、源码发现、论文结果或数据开始；
- 文章围绕方案判断时，直接说明设计选择及其约束；
- 用户已经提供具体故障、问题或材料时，简短承接真实上下文。

这些方式不是固定模板，也不要为了变化而机械轮换。选择标准只有一个：哪种方式能让读者最短地进入文章真正要讨论的问题。

禁止使用以下作者开头：

- “假设一个……”；
- “想象一下……”；
- “随着……快速发展”；
- “在当今时代”；
- “我们都知道”；
- 用连续设问代替主题说明；
- 编造戏剧化事故、故障或风险，再勉强连接一个简单主旨；
- 为吸引注意而制造并不存在的反常识、危机感或悬念。

除非文章正在引用并分析原文，否则不要原样使用这些句式。需要讨论条件场景时，直接写条件和结果，例如把“假设一个 Agent 正在修改代码”改为“当 Agent 在一次运行中多次修改代码时，后续模型调用需要看到哪些状态？”

具体例子可以放在真正需要建立直觉的章节，但不默认放在开头。优先使用真实、可核对或由用户提供的例子；简单主旨直接说明，不为增加篇幅或故事感制造场景。

## 写出专业而直白的正文

遵循 [references/writing-principles.md](references/writing-principles.md) 的白描原则：

- 直接写清对象、动作、条件、原因和结果；
- 已有准确的专业术语时继续使用，并在首次出现时就地解释；
- 没有必要使用术语时，选择具体、通用、不会引起歧义的词；
- 标题直接说明本节问题或内容，不用新闻式悬念和故作高深的口号；
- 让过渡来自内容关系，说明上文解决了什么、还留下什么、下文为何出现；
- 让抽象结论获得足够的事实、机制、数据或例子支撑；支撑材料出现在哪里，由论述需要决定；
- 只保留能改变理解的源码和实现细节，不用函数名堆砌专业感；
- 避免固定排比、过度加粗、连续口号、空泛结语和反复套用同一种句式。

白描不等于口语随意化。准确性优先；在准确的前提下，使用最直接、最容易形成共同理解的表达。

## 选择并组织图表

不要因为技术文章“应该有图”而画图。绘图前先明确：

1. 纯文字为什么不足以清楚呈现这里的关系？
2. 图要揭示什么？
3. 读者看完图应获得什么认识？

三个问题回答不清楚时，不使用图。

根据实际关系选择形式：

- 时间、调用和参与者交互：时序图或时间线；
- 状态及转换：状态图；
- 条件、分支和执行路径：流程图；
- 层级、包含和归属：树状图或分层图；
- 多项精确映射和对照：表格；
- 数值变化、分布和相关性：统计图表。

限定每张图的表达范围。入门主图只展示建立心智模型所需的主干；生产异常、恢复分支和局部细节放在真正讨论它们的位置。不要让局部图冒充完整系统，也不要把所有可能路径塞进一张图。

让图和正文分别承担大部分解释：

- 图负责整体关系、结构、时序或变化；
- 正文负责原因、边界、取舍和结论；
- 正文不逐节点机械复述图片；
- 图中也不能缺少理解主旨所必需的关键关系。

使用图后检查标签、箭头、阅读方向、信息密度、章节位置和上下文衔接。能实际渲染时进行视觉检查；不能渲染时至少检查图的语法与关系是否自洽。

## 重构现有文章

不要收到局部批评后立刻只改句子。先诊断问题所在层级：

1. **全文主题**：中心问题是否清楚，内容是否越界；
2. **章节职责**：这一节是否有存在价值，是否与上下文重复；
3. **论述方式**：是否缺少例子、证据、原理或实现边界；
4. **图文关系**：是否需要图，图的类型和范围是否正确；
5. **表达方式**：是否机械、空泛、新闻化或术语堆叠。

如果诊断结果需要重写主体、移动或增删章节、改变内容边界或调整论述主线，先按“形成并确认文章大纲”完成双向推演和用户确认，再修改正文。只涉及不改变结构的局部表达时可以直接处理。

先决定保留、删除、合并、移动还是重写，再进行语言修改。完成局部重构后同步检查标题编号、开篇预告、过渡、交叉引用、结语、面试回答或摘要，避免正文与外围内容失去一致性。

## 完成审稿

按顺序完成七轮语义审查：

1. **主题审查**：全文和每节是否言之有物，是否真的增加认识；
2. **大纲对照**：每节是否兑现已确认的主旨和读者收益；出现实质偏离时，修正正文，或在确有必要时重新确认大纲并向用户说明；
3. **关系审查**：章节是否自然递进、呼应或形成必要对照；
4. **开头审查**：是否采用最短进入方式，是否出现被禁止的 AI 式套话、连续设问或虚构戏剧场景；
5. **来源审查**：来源是否自然归属，是否出现审计式证据声明、无意义本地链接或过度源码索引；
6. **表达审查**：是否准确、直白、顺畅，术语是否必要且解释充分；
7. **图文审查**：图是否必要、选型和范围是否正确、是否与正文互补。

逐段尝试用一句具体的话复述它讲了什么。只能复述抽象标签、无法说出对象和结论时，重写该段。

最后检查 Markdown 标题层级、代码围栏、链接、引用、图片资源和占位符。确认公开链接离开本地仓库后仍可访问，文章中没有本地源码路径链接。除非用户明确要求只审查，否则完成整个文章文件，不留下待补章节。

## 交付

返回可点击的 Markdown 文件路径，并简要说明：

- 文章的中心主旨；
- 主要章节采用了什么论述关系；
- 使用了哪些图表，以及它们分别解决什么理解问题；
- 相对已确认大纲是否存在实质偏离，以及如何处理；
- 仍然存在但没有擅自补写的证据限制。

不要把工具日志、逐步执行记录或完整内部写作契约写入正式文章。
