# 通用技术文章写作

把技术材料写成读者能够理解、读起来顺畅、同时保持专业准确的完整文章。不要从固定文类模板出发；从当前主题、读者要获得的认识和内容之间的真实关系出发。

## 读取参考资料

开始写作或重构前，完整阅读 [references/writing-principles.md](references/writing-principles.md)。它定义“言之有物”、白描式技术表达和图文互补的具体判断方法。

遇到以下情况时，再完整阅读 [references/case-study.md](references/case-study.md)：

- 文章主题或章节职责难以确定；
- 内容虽然技术上正确，却显得空泛、机械或难以理解；
- 不确定某一节应保留、合并、删除还是重写；
- 不确定是否需要图、应使用什么图，或图文怎样分工；
- 需要从反复返工的技术文章中吸取写作经验。

不要把案例文章的目录、章节或写法当成模板。案例用于识别问题和理解判断过程。

## 确定任务与产物

1. 阅读当前仓库的 `AGENTS.md`、目标目录约定、输入材料和未提交改动。
2. 判断任务属于以下哪种入口：
   - **从零写作**：从主题、问题、资料、源码或论文形成完整文章；
   - **重构文章**：诊断并修改现有草稿或成品；
   - **审查文章**：只报告问题时不改文件；用户明确要求重写、润色或完善时才修改。
3. 优先使用用户指定的输出路径。用户要求完整文章但未指定路径时：
   - 遵守仓库已有正式产出目录及命名约定；
   - 没有仓库约定时，在当前工作目录创建能表达主题的 kebab-case Markdown 文件；
   - 新建文章不覆盖同名文件；重构任务只修改用户指定的文章。
4. 默认交付完整 Markdown，不只交付提纲、片段或写作建议。
5. 保留用户已有且与本次任务无关的改动，不自动修改原始资料、参考仓库或中间草稿。

## 建立写作契约

先从请求和材料中推断以下内容：

- 文章要回答的中心问题；
- 目标读者已经知道什么、目前缺少什么；
- 读完后应获得的理解、判断能力或行动能力；
- 内容范围以及明确不展开的旁支；
- 需要使用的事实、源码、论文、例子和图表；
- 篇幅、语气、发布场景和引用要求。

只有缺失信息会实质改变中心问题、读者定位、内容边界或证据标准时，才集中提出少量问题。能够通过仓库、材料或现有文章发现的事实不要询问用户。

不要把宽泛主题名当成文章主旨。例如，“流式输出”只是领域，“模型响应分批到达时，什么时候可以推动工具执行”才是可以组织论述的问题。

## 研究并管理证据

1. 先使用用户提供的材料和本地源码。需要外部事实、最新实践或未提供的论文时，再查找一手资料。
2. 将准备写入文章的内容区分为：
   - **可验证事实**：源码、论文、官方文档或可核对数据直接支持；
   - **基于证据的推断**：由事实推导，但不是来源原文或项目现状；
   - **工程或写作建议**：作者提出的选择和取舍；
   - **未验证结论**：证据不足，不能写成确定事实。
3. 引用本地源码时记录仓库、相对路径、关键符号和 commit；引用论文或网页时保留原始链接。
4. 不为显得权威而堆砌引用。引用应支撑关键事实、边界和有争议的判断。
5. 如果来源没有实现某项能力，直接说明实现边界，不用一套自创方案填充后再写成来源事实。

## 建立文章主线

先写出一条内部主线，不必原样放进正文：

`读者从什么问题出发 → 经过哪些必要认识 → 最终能够理解或判断什么`

再为每个候选章节回答：

1. 这一节具体讲什么？
2. 为什么全文需要它？
3. 它给读者增加什么新认识？
4. 它与前后内容是什么关系？
5. 用什么事实、推理、例子或图表讲清楚？

根据答案组织章节。可用的关系包括递进、因果、问题与解决、整体与局部、对照、回扣和从具体到抽象，但不要为了形式整齐强行使用同一种关系。

删除或合并以下内容：

- 没有独立问题和新认识的章节；
- 只是换一组术语重复前文的总结；
- 引入问题却没有解释原理、实现边界或解法的段落；
- 为了“完整”而偏离中心问题的旁支；
- 只有函数名、类型名和源码细节，却没有说明这些细节解决什么问题的内容。

提纲是论述关系的结果，不是写作起点。不要为源码分析、论文解读、方案设计等任务预设固定目录。

## 写出专业而直白的正文

遵循 [references/writing-principles.md](references/writing-principles.md) 的白描原则：

- 直接写清对象、动作、条件、原因和结果；
- 已有准确的专业术语时继续使用，并在首次出现时就地解释；
- 没有必要使用术语时，选择具体、通用、不会引起歧义的词；
- 标题直接说明本节问题或内容，不用新闻式悬念和故作高深的口号；
- 让过渡来自内容关系，说明上文解决了什么、还留下什么、下文为何出现；
- 用具体例子帮助读者形成认识，再上升到必要抽象；
- 只保留能改变理解的源码和实现细节，不用函数名堆砌专业感；
- 避免固定排比、过度加粗、连续口号、空泛结语和反复套用同一种句式。

白描不等于口语随意化。准确性优先；在准确的前提下，使用最直接、最容易形成共同理解的表达。

## 选择并组织图表

不要因为技术文章“应该有图”而画图。绘图前先明确：

1. 纯文字为什么不足以清楚呈现这里的关系？
2. 图要揭示什么？
3. 读者看完图应获得什么认识？

三个问题回答不清楚时，不使用图。

根据实际关系选择形式：

- 时间、调用和参与者交互：时序图或时间线；
- 状态及转换：状态图；
- 条件、分支和执行路径：流程图；
- 层级、包含和归属：树状图或分层图；
- 多项精确映射和对照：表格；
- 数值变化、分布和相关性：统计图表。

限定每张图的表达范围。入门主图只展示建立心智模型所需的主干；生产异常、恢复分支和局部细节放在真正讨论它们的位置。不要让局部图冒充完整系统，也不要把所有可能路径塞进一张图。

让图和正文分别承担大部分解释：

- 图负责整体关系、结构、时序或变化；
- 正文负责原因、边界、取舍和结论；
- 正文不逐节点机械复述图片；
- 图中也不能缺少理解主旨所必需的关键关系。

使用图后检查标签、箭头、阅读方向、信息密度、章节位置和上下文衔接。能实际渲染时进行视觉检查；不能渲染时至少检查图的语法与关系是否自洽。

## 重构现有文章

不要收到局部批评后立刻只改句子。先诊断问题所在层级：

1. **全文主题**：中心问题是否清楚，内容是否越界；
2. **章节职责**：这一节是否有存在价值，是否与上下文重复；
3. **论述方式**：是否缺少例子、证据、原理或实现边界；
4. **图文关系**：是否需要图，图的类型和范围是否正确；
5. **表达方式**：是否机械、空泛、新闻化或术语堆叠。

先决定保留、删除、合并、移动还是重写，再进行语言修改。完成局部重构后同步检查标题编号、开篇预告、过渡、交叉引用、结语、面试回答或摘要，避免正文与外围内容失去一致性。

## 完成审稿

按顺序完成四轮语义审查：

1. **主题审查**：全文和每节是否言之有物，是否真的增加认识；
2. **关系审查**：章节是否自然递进、呼应或形成必要对照；
3. **表达审查**：是否准确、直白、顺畅，术语是否必要且解释充分；
4. **图文审查**：图是否必要、选型和范围是否正确、是否与正文互补。

逐段尝试用一句具体的话复述它讲了什么。只能复述抽象标签、无法说出对象和结论时，重写该段。

最后检查 Markdown 标题层级、代码围栏、链接、引用、图片资源和占位符。除非用户明确要求只审查，否则完成整个文章文件，不留下待补章节。

## 交付

返回可点击的 Markdown 文件路径，并简要说明：

- 文章的中心主旨；
- 主要章节采用了什么论述关系；
- 使用了哪些图表，以及它们分别解决什么理解问题；
- 仍然存在但没有擅自补写的证据限制。

不要把工具日志、逐步执行记录或完整内部写作契约写入正式文章。
