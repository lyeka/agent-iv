# 技术文章写作判断原则

本文档用于判断文章是否真正讲清楚了内容。它不提供固定目录，也不要求每篇文章使用同一种论证结构。

## 一、什么叫言之有物

### 主题不是领域名称

“数据库”“流式输出”“Agent 状态机”“某篇论文”只是材料范围，不是文章真正要说的话。文章主题至少应包含：

- 读者面对的具体问题；
- 文章准备给出的核心认识；
- 这个认识为什么值得解释。

例如：

- 空泛主题：`流式输出`。
- 可论述主题：`模型响应分批到达时，运行时应在什么时点确认消息和启动工具`。

后者能够决定材料取舍，也能判断哪些异常处理属于主题、哪些已经越界。

### 言之有物意味着读者获得了变化

一段内容有价值，不取决于字数、术语数量或引用数量，而取决于读者读完后是否多获得了一项具体认识：

- 知道一个概念究竟指什么；
- 理解一段机制为什么这样运行；
- 能区分两个容易混淆的对象；
- 能判断某种方案何时适用；
- 能沿着证据得到一个结论；
- 能把结论用于新的问题。

如果一节结束后，读者只能记住几个抽象名词，却说不出它解决了什么问题，这一节仍然是空的。

### 内容不等于信息堆积

源码细节、论文术语、行业做法和边界情况都可能是真的，但真实不代表都应写入。材料只有在承担以下作用时才进入正文：

- 解释核心机制；
- 支撑关键结论；
- 帮助建立例子；
- 澄清容易误解的边界；
- 形成必要对照；
- 推动下一个问题自然出现。

不能说明作用的材料，先删除或放回资料区，不要为了显得全面塞进文章。

## 二、怎样组织整体与章节

### 先确定全文的起点和终点

正式写作前，先说明：

- 文章要回答的中心问题；
- 准备给出的核心认识或判断；
- 读者已有的背景和当前缺少的认识；
- 读完后能够理解、判断或完成什么；
- 文章讲什么、明确不讲什么；
- 用什么方式最短地进入主题；
- 最后收束到什么结论。

再写出读者的理解路径：

`读者最初怎样理解这个问题，文章希望他最后怎样理解，中间必须跨过哪些认识台阶。`

这些“台阶”才可能成为章节。它们不一定对应统一格式，也不必数量对称。

常见关系包括：

- **递进**：先建立最小模型，再加入现实限制；
- **因果**：先说明现象，再追到机制和结果；
- **问题与解决**：先明确失败在哪里，再说明可行处理；
- **整体与局部**：先看完整结构，再放大关键步骤；
- **对照**：用差异帮助读者理解选择和边界；
- **回扣**：后文用新证据重新解释开篇问题；
- **从具体到抽象**：先用 API、代码或案例形成直觉，再提炼通用认识。

同一篇文章可以混合这些关系。重要的是关系真实存在，而不是目录看起来整齐。

### 给每节定义职责和位置

写作前，为每节回答：

| 判断 | 要回答的问题 |
|---|---|
| 暂定标题 | 怎样直接概括本节问题或内容？ |
| 具体主旨 | 这一节准备论证什么？ |
| 新增认识 | 读者读完比进入本节前多理解了什么？ |
| 支撑方式 | 使用哪些事实、机制、数据、源码、论文、例子或图表？ |
| 上下文关系 | 它承接上文什么，又为下文准备什么？ |
| 当前位置 | 为什么必须放在这里，而不是更早、更晚或相邻章节？ |
| 图表任务 | 是否需要图表；如果需要，它要解释什么关系？ |

这张表只用于推演结构和与用户确认。它不要求原样出现在文章中，也不能变成所有文章或所有章节的固定模板。

### 从前往后推演读者怎样理解

从读者起点开始，逐节检查：

1. 读者进入这一节前是否已经具备必要前提；
2. 这一节是否增加了前文没有的新认识；
3. 论点是否有足够材料支撑；
4. 它是否自然承接上一节；
5. 它是否为下一节提供必要基础；
6. 是否过早引入尚未解释的抽象、术语或复杂分支；
7. 是否与前文重复，或者放到其他位置同样成立。

如果读者必须依赖后文知识才能理解当前章节，顺序很可能反了。如果一节没有新增认识，先判断它应当删除、合并，还是改成真正承担前后关系的章节。每次调整后都从读者起点重新顺推，不能只检查刚改过的局部。

### 从后往前反推结论怎样成立

从结尾和读者终点开始，逆序检查：

1. 最终结论依赖哪些前提和证据；
2. 靠近结尾的章节是否真正支撑结论；
3. 每节提供的认识是否在后文得到使用；
4. 删除某一节后，最终结论是否仍然成立；
5. 将某一节前移或后移后，论证是否更自然；
6. 是否缺少支撑关键结论的中间环节；
7. 开头承诺的问题是否在后文得到完整回答。

删除测试用于判断必要性，移动测试用于判断位置。删除后全文仍完全成立的章节通常没有独立贡献；移动到多个位置都不影响理解的章节通常职责不清。它们可能包含正确内容，但仍应删除、合并或重新定位。

### 判断大纲是否稳定

满足以下条件，才开始正式正文：

- 全文主旨能够用一句具体的话说明；
- 每节都有唯一且可以复述的贡献；
- 读者获得的认识逐步增加，没有明显跳跃；
- 各节存在明确的递进、因果、对照、整体与局部或问题与解决关系；
- 没有为了“完整”而加入的旁支；
- 没有只承担空泛总结、升华或过渡的章节；
- 开头、主体和结尾回答同一个中心问题；
- 图表计划与章节主旨一致；
- 正向和反向检查不再要求实质调整章节。

### 在正式写作前确认大纲

完整新文章、主体重写和结构调整都应先把全文主旨、章节职责和排列关系展示给用户确认。展示双向推演后的最终结果和关键调整即可，不需要暴露冗长的内部思考过程。

用户修改大纲后，再做一轮正向与反向检查。用户已经给出并批准了信息完整的大纲时，只需检查是否有实质结构问题；没有问题就直接采用。用户明确要求跳过确认时，仍应在内部完成双向推演。

确认前可以继续研究和核实事实，但不要开始正式写作或结构重构。写作中只有新证据改变全文主旨、内容边界或主要章节关系时，才需要暂停并重新确认；局部例子、措辞和段落位置不需要反复询问。

### 识别没有存在价值的章节

出现以下情况时，优先删除或合并：

- 标题只能写成“总结”“进一步思考”“升华”，但说不出新增认识；
- 把前文结论换成类型名、原则或口号再次排列；
- 同时承担总结、设计、实现、检查清单和过渡，导致主旨无法辨认；
- 引出一个困难，却没有说明来源是否解决、文章建议如何解决以及两者边界；
- 为了覆盖更多主题而引入上下文工程、测试或工具设计等旁支；
- 内容放在相邻章节同样成立，说明它没有明确位置。

删除并不表示内容不正确，只表示它在当前文章中没有独立作用。

### 让过渡来自逻辑

有效过渡通常包含三件事：

1. 上一部分已经解决什么；
2. 仍然缺少什么；
3. 下一部分为什么能补上。

例如：

> 停止字段只能说明一次模型响应为什么结束。要判断整个任务是否完成，还需要把工具结果、用户消息和运行限制放回完整循环中。

这类过渡本身就在推进理解。单纯写“接下来进一步探讨”没有提供关系。

## 三、怎样自然开始文章

### 开头先让读者进入问题

技术文章的开头不负责表演文采，也不需要先讲一个故事。它只需要用最短路径完成当前文章真正需要的准备，例如：

- 直接说明文章要解决什么问题；
- 核心结论足够清楚时，先说结论再解释；
- 术语容易混淆时，先界定概念和范围；
- 从已经存在的事实、源码发现、论文结果或数据开始；
- 文章围绕方案选择时，直接说明选择和约束；
- 用户已经提供真实问题或故障时，简短承接该上下文。

不要把这些方式做成轮换模板。先问“读者在进入正文前缺少哪一步理解”，再选择最短的开头。

简单主旨通常只需要一两段直陈。复杂主题也不必先编造故事；可以先说明核心问题，再在真正需要形成直觉的章节使用例子。

### 禁止套话式和戏剧化开头

以下写法不作为作者的文章开头：

- “假设一个……”；
- “想象一下……”；
- “随着……快速发展”；
- “在当今时代”；
- “我们都知道”；
- 连续抛出多个问题，却不说明文章的中心问题；
- 编造事故、故障或高风险场景，再勉强连接一个简单主旨；
- 制造并不存在的反常识、危机感或悬念。

除非文章正在引用并分析原文，否则不要原样使用这些句式。

需要讨论条件时，直接写条件和结果：

- 不写：`假设一个 Agent 正在修改代码。`
- 改写：`当 Agent 在一次运行中多次修改代码时，后续模型调用需要看到哪些状态？`

需要说明行业变化时，写清具体变化以及它造成的影响，不用“随着……快速发展”代替事实。

需要表达普遍认识时，直接陈述结论并给出依据，不用“我们都知道”替读者作判断。

需要引出多个问题时，先给出中心问题，再把其余问题组织进正文，不用连续设问制造气氛。

### 例子不是固定开头

例子适合帮助读者理解复杂关系，但应满足至少一项：

- 它来自真实材料或用户提供的上下文；
- 它能够准确代表文章要解释的机制；
- 后文会继续使用它，而不是开头结束后就被丢弃；
- 没有它，读者确实难以建立必要直觉。

例子不满足这些条件时，直接进入问题。

抽象结论需要事实、机制、数据或例子支撑，但支撑材料可以出现在正文最需要的位置。不能把“具体材料有助于理解”误写成“所有文章必须从假设场景开始”。

## 四、怎样自然说明来源

### 把研究过程留在后台

内部研究需要详细记录来源、版本、路径、关键符号和结论性质，正式文章不需要展示这套台账。读者需要知道结论来自哪里，但不需要看到作者怎样管理证据。

因此，不创建“证据范围”“证据边界”“本文使用哪些源码，哪些结论是推断”等独立声明。来源归属应进入正常句子：

- `PI 的实现会在每次模型调用前刷新当前工具集合。`
- `从 PI 与 Claude Code 的处理可以看到，请求视图和完整会话状态不是同一个对象。`
- `如果自行设计，更稳妥的做法是在执行工具前重新检查权限。`

这些句子分别表达项目行为、基于实现得到的认识和文章建议，不需要额外贴标签。

### 把来源放在它真正起作用的位置

- 来源贯穿全文时，先建立文章主题，再用一句话说明主要参考哪些项目或论文。
- 来源只支撑一个章节时，在第一次讨论相关内容时引入。
- 来源只是延伸阅读时，只在相关结论附近或文末参考资料出现。
- 版本、快照性质或实现缺失确实限制结论时，在第一次使用来源附近用一句短说明交代。

不要让来源说明抢占开头，也不要在文章开始前罗列 commit、日期、文件和结论分类。

### 只提供发布后仍有意义的链接

内部工作记录可以使用本地相对路径或绝对路径，发布文章不可以。文章离开工作区以后，`/Users/...`、`../related-repos/...` 等链接对读者没有意义。

使用以下规则：

- 公开源码存在稳定地址时，链接公开页面，优先固定到具体 commit；
- 本地或非公开源码只写项目名、版本和必要符号，不生成路径链接；
- 不能确认公开地址时不猜测或拼造链接；
- 文末只列真正有助于继续阅读的公开项目、论文和官方文档；
- 不自动生成逐文件、逐函数的源码索引。

证据可追溯和链接可访问是两个问题。内部记录保证作者能复核，公开链接保证读者能继续阅读；不能用前者替代后者。

## 五、怎样使用白描式技术表达

### 白描是具体，不是粗糙

白描式技术表达直接说明：

- 谁或什么在行动；
- 做了什么；
- 在什么条件下做；
- 为什么这样做；
- 产生什么结果。

它不排斥专业术语，也不把复杂问题说得幼稚。它拒绝的是用抽象词代替具体解释。

例如：

- 模糊：`运行时完成统一裁决。`
- 具体：`记录完工具结果后，运行时检查是否还有后续工作，并决定是否进入下一轮。`
- 模糊：`系统执行异常对账。`
- 具体：`模型流中断后，系统确认哪些工具尚未启动、哪些正在执行，并为已经记录的调用补上结果。`

后者不一定更短，但读者能看到真实动作。

### 专业术语应当准确落地

已有通行术语时不要生造替代词。首次出现时回答：

1. 中文含义是什么；
2. 它在当前问题中负责什么；
3. 有什么短例子能帮助理解。

解释后统一使用同一个名称，不在多种近义译法之间来回切换。

专业术语用于压缩已经解释清楚的概念，不能用于遮盖没有解释清楚的内容。

### 标题直接说明内容

标题应帮助读者预测这一节会得到什么。优先使用：

- `模型响应被截断后怎样处理`；
- `Fallback 发生时怎样处理旧 attempt`；
- `流式响应在 Agent loop 中怎样处理`。

谨慎使用：

- “最危险的不是……”；
- “别让……欺骗你”；
- “真正的秘密……”；
- 与内容并不完全对应的口号或悬念。

标题可以有节奏和辨识度，但不能让修辞压过含义。

### 控制机械和 AI 式表达

重点检查：

- 每段都用“首先、其次、最后”；
- 频繁使用“不是……而是……”制造虚假对立；
- 为普通结论安排整齐的三段式排比；
- 大量加粗小标题把正文切成碎片；
- 每节结尾都重复一句口号；
- 使用“赋能、闭环、范式、统一裁决、深度融合”等词，却没有具体动作；
- 句子长度、段落结构和语气完全一致；
- 用“显而易见”“不难发现”跳过真正解释。

修正时不要只替换关键词。重新写清对象、条件、动作和原因，让句子因内容需要而长短变化。

### 技术细节服务于理解

保留函数名、类型、字段或代码片段，需要至少满足一项：

- 它是结论的直接证据；
- 它揭示了控制顺序或边界；
- 它帮助读者继续阅读源码；
- 不展示它就无法解释关键差异。

如果只需描述一个简单行为，白描说明项目怎样处理即可，不必列出函数调用链。

## 六、怎样选择和组织图表

### 先判断是否需要图

图适合呈现文字难以快速建立的关系，例如：

- 多个参与者之间的调用顺序；
- 状态在事件发生后的变化；
- 条件分支和回路；
- 三层以上的包含或归属；
- 多项字段或行为的精确对照；
- 数据趋势、分布和相关性。

单一事实、两步操作或简短判断通常不需要图。图不能因为“技术文章需要配图”而存在。

### 用关系选择图，不用偏好选择图

| 要呈现的关系 | 优先形式 | 重点 |
|---|---|---|
| 参与者随时间交互 | 时序图 | 谁先做什么、等待什么 |
| 状态与转换条件 | 状态图 | 当前状态、触发事件、合法去向 |
| 判断、执行路径和回路 | 流程图 | 条件如何改变下一步 |
| 层级、包含和所有权 | 树状图、分层图 | 谁包含谁、谁负责什么 |
| 多项精确映射或比较 | 表格 | 对齐字段、差异和结果 |
| 数值变化与分布 | 折线图、柱状图、散点图等 | 尺度、趋势和异常 |

如果真正要表达的是 `run 包含 turn，turn 又包含 model attempt`，使用包含结构比把三者画成并列步骤更准确。

### 每张图只承担一个主旨

画图前写一张内部说明：

- 这张图回答什么问题；
- 图从哪里开始，到哪里结束；
- 必须出现哪些关系；
- 哪些异常或细节明确不画；
- 读者看图后应能复述什么。

例如，介绍核心循环的主图只需呈现准备、模型响应、工具执行、结果记录和下一轮。重试、fallback、截断和中断恢复应在后续章节单独展开。把所有生产分支提前塞进主图，会破坏初次理解。

### 图文应当互相增强

理想关系不是“一图胜千言”，也不是“图只是正文装饰”：

- 单看图，读者能理解主要关系和方向；
- 单看正文，读者能理解主要过程和结论；
- 两者结合，读者还能理解原因、边界、取舍和容易误解之处。

正文不要逐个复述节点。可以沿着图的主线解释最重要的变化，再说明图为了保持聚焦而省略了什么。

图也不能只画几个名词，把所有箭头含义留给正文补充。必要的方向、条件和范围应直接体现在图中。

### 检查图的呈现

完成后检查：

- 图的类型是否与关系一致；
- 标题是否准确说明图的主题；
- 起点、终点、主路径和回路是否清楚；
- 箭头是否存在方向或语义歧义；
- 标签是否使用读者已经理解的词；
- 节点是否过多，异常分支是否喧宾夺主；
- 图放在正文中的位置是否自然；
- 图后的文字是否解释原因和边界，而非机械复述。

## 七、怎样审查一篇文章

按下面顺序审查，不要先做措辞润色：

### 1. 主题审查

- 中心问题是否明确？
- 文章是否给出了核心认识？
- 内容是否围绕主旨取舍？
- 读者读完后获得了什么变化？

### 2. 大纲一致性审查

- 全文是否仍在回答已确认的中心问题？
- 每节是否兑现了约定的具体主旨和读者收益？
- 正向阅读是否存在知识跳跃、重复或顺序倒置？
- 从结论反推时，每节是否仍然必要并得到后文使用？
- 正文若实质偏离大纲，是正文应修正，还是证据确实要求重新确认大纲？

能够修正的偏离直接修正；确因新证据保留的实质偏离，应重新确认或在交付时向用户说明，不能静默改变已经确认的论述主线。

### 3. 开头审查

- 是否用最短方式进入中心问题？
- 是否出现被禁止的套话、连续设问或虚构戏剧场景？
- 是否为了显得生动而让开头比主题本身更复杂？
- 开头使用的上下文是否真实，并在后文继续发挥作用？

### 4. 章节审查

- 每节是否有独立职责？
- 是否增加了前文没有的新认识？
- 与前后内容的关系是否清楚？
- 是否存在应该删除的总结、旁支或重复？

### 5. 论述与来源审查

- 结论是否有事实、推理、例子或对照支撑？
- 是否先提出抽象定义，却没有给读者形成直觉的材料？
- 来源事实、文章推断和建议是否分开？
- 引出的难题是否真正回答？
- 是否把内部研究过程写成“证据范围”或审计式声明？
- 来源是否放在最接近相关结论的位置？
- 是否存在发布后无法访问的本地源码链接？
- 文末参考资料是否只保留真正有用的公开来源？

### 6. 表达审查

- 能否用具体对象和动作复述每段？
- 专业术语是否必要、准确并就地解释？
- 标题是否直白对应正文？
- 过渡是否真的推进逻辑？
- 是否存在机械句式、空泛概念和刻意拔高？

### 7. 图文审查

- 每张图是否必要？
- 图形类型和表达范围是否正确？
- 图和正文能否各自解释主要内容？
- 组合后是否增加了新的理解，而非简单重复？

技术正确只是文章成立的前提。读者能否沿着作者组织的路径形成完整认识，才是最终判断。
