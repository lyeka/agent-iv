# Agent 核心执行循环文章的写作与返工案例

## 案例边界

- Codex 任务：`撰写 Agent 核心执行循环文章`，任务 ID `019ffe86-a862-7cd3-b15d-8957a78dbde4`。
- 当前成品：[output/agent-execution-loop.md](../../../../output/agent-execution-loop.md)。
- 主要材料：PI 固定 commit 的源码、Claude Code 非官方公开源码快照、Anthropic、OpenAI 和 AWS 一手资料。
- 原始目标：用源码说明 Agent 核心执行循环如何实现、为什么这样实现，并提供适合面试口述的回答。

这不是一篇“成功范文解析”。任务经历了大量返工，真正有价值的部分是：技术事实基本正确以后，文章为什么仍然难读；用户怎样识别主题、结构、表达和图文上的问题；哪些中间方案最终被删除。

本文按重要修改的实际先后关系整理，不记录工具日志、重复计划和文件操作。

## 1. 从研究和大纲开始

### 原方案

任务开始后先检查本地仓库、参考源码版本和正式文章位置，再围绕以下问题定位源码：

- 一次 loop 包含哪些步骤；
- 模型停止信号怎样解释；
- 步数、token、成本和用户中断在哪里控制；
- 截断、fallback、流式输出和结构化输出怎样处理；
- 哪些错误能重试，怎样限制重试和避免重复副作用。

第一版计划采用“直观故障 → 最小循环 → 生产问题 → 通用状态机 → 面试回答”的长文结构，并要求区分源码事实、工程推断和推荐设计。

### 有效之处

- 先固定 PI 和 Claude Code 快照的 commit，避免引用漂移。
- 使用源码作为主体、官方资料作为协议和最佳实践补充。
- 把 run、turn、model attempt 和 tool batch 分开，为后续讨论重试和预算建立共同语言。
- 从一开始就保留事实、推断和建议的边界。

### 暴露的问题

研究问题几乎全部进入了目录。大纲看起来全面，却默认“每一个研究点都需要一节”，没有充分判断章节在全文中的职责。后续多个返工都源于这个问题：材料完整不等于文章结构成立。

### 可迁移认识

研究清单用于保证材料充分，不能直接充当文章目录。目录必须根据读者需要形成的认识重新组织。

## 2. 第一版长文：内容齐全，但写作视角和呈现方式仍未成立

### 原方案

初稿写成两部分：

1. PI 与 Claude Code 的源码实现和设计原因；
2. 三到五分钟面试总答与九个高频追问。

文章加入 Mermaid 状态机、自定义状态类型、术语解释、源码链接和外部一手资料。

### 用户反馈

用户连续指出两类问题：

- 回答大量使用“我会这样设计”“我会记录”等第一人称，好像文章作者参与过 PI 或 Claude Code 的实现；
- 高频追问分成“直接回答”和“源码加分点”，读起来像两份拼接材料，不像自然口述。

### 最终修改

- 全文改为第三方分析视角，将项目行为归属于 PI 或 Claude Code，将文章结论写成推荐做法。
- 删除“直接回答”“源码加分点”等固定标签，把结论、证据和原因组织成连续回答。

### 可迁移认识

叙述视角必须与证据身份一致。没有参与项目实现，就不能借面试口吻把源码选择说成个人工程经历。

分栏和标签只有在真的帮助理解时才使用。把观点和证据机械分开，可能破坏自然论述。

## 3. 核心循环状态图：完整不等于适合当前位置

### 原方案

初稿的核心循环图试图同时容纳：

- 正常模型调用；
- 工具执行；
- 请求重试；
- 截断；
- fallback；
- 中断恢复；
- 最终结束。

后来又把图扩展为十个生产级状态，包括准备重试、处理中断后的状态等。

### 用户反驳

用户指出，这张图所在章节的任务只是建立一个“简化但完整的 Agent loop”。生产异常应在后文展开。图覆盖的情况越多，越偏离它在文章中的位置。

用户还提出：

- 图下正文不能只是给节点补名词、代码细节或遗漏路径；
- 单看图或单看文字，都应理解七八成；结合后才形成完整认识；
- 不是所有图都要展示所有情况，图的范围取决于当前表达目标。

### 最终修改

核心图收缩为七个状态：

- 准备本轮；
- 调用模型；
- 处理模型响应；
- 检查并执行工具；
- 记录工具结果；
- 判断继续还是结束；
- 结束运行。

网络重试、截断、fallback 和中断恢复从引导图移出，留给后续章节。

### 可迁移认识

图的“完整”是相对于章节主旨完整，不是相对于整个系统完整。

介绍性图负责建立第一层心智模型。生产故障图负责解释异常关系。两种图不能因为对象相同就强行合并。

正文与图应当互相增强，而不是一方替另一方补漏。

## 4. 全文语言审查：抽象词准确吗，读者看见动作了吗

### 原方案

文章使用了“结果落账”“异常对账”“统一裁决”“响应落稳”“工具预检”“硬边界”等表达。它们看起来简洁、专业，但没有直接说明程序做了什么。

### 用户反驳

用户明确要求不要追求“高大上”，而要在通用准确的前提下通俗易懂。问题不是几个关键词，而是全文习惯用抽象名词替代具体动作。

### 最终修改

文章逐段改写，而不是批量替换：

- “结果落账”改为“记录工具结果”；
- “异常对账”改为“处理中断后的状态”并说明具体处理；
- “统一裁决”改为“判断继续还是结束”；
- “响应落稳”改为“整理并确认模型响应”；
- “工具预检”改为“检查工具调用”；
- “硬边界”改为具体的强制停止条件。

同时处理了第一人称、空泛口号、术语首次出现没有解释和新闻式标题等问题。

### 可迁移认识

白描不是把文章写得浅，而是直接写出对象、动作、条件和结果。

抽象词只有在具体机制已经解释清楚以后，才能用来压缩表达。不能先发明一个概念，再让读者猜它包含哪些动作。

语言问题往往是思考问题的表面表现。无法用具体动作重写一句话，通常说明作者还没有明确这一段真正想说什么。

## 5. 停止判断章节：从抽象分类回到具体问题

这是整个任务中返工最多的部分。

### 5.1 初版：多层共同判断，但内容过散

初版试图同时说明 provider、adapter、loop、tool executor 和上层应用怎样产生停止信号。事实基本正确，但读者无法获得一个可以使用的判断顺序。

用户追问：“这章应该表达什么，怎么表达才言之有物？”

### 5.2 尝试用三种结果建模

中间方案提出 Recover、Continue、Stop，后来又定义 `ResponseDisposition`、`RunDecision`、`TerminalReason` 等类型。

用户继续追问：

- 三种结果来自哪里；
- 是否足够、合理、全面；
- 这些定义是不是源码事实；
- `suspend` 是否有必要在核心 loop 中出现。

检查后发现，三种结果混合了模型响应处理和整个 run 的控制动作。`suspend` 属于人工审批、异步任务和持久化恢复，并不是本文核心循环必须解释的状态。

这些抽象最终被删除。

### 5.3 改用 Anthropic `stop_reason` 具体举例

章节从一条 `tool_use` API 响应开始：

- 模型已经停止生成；
- 任务却没有结束；
- 应用仍需执行工具并返回结果。

正文再说明不同 provider 的字段并不统一，adapter 只能统一表示，不能替代对实际响应内容的检查。

这一修改解决了“抽象先于直觉”的问题。

### 5.4 3.3 的多次图文重构

为了从单次响应上升到整个 run，中间尝试过：

- 简单流程图；
- “两道门”图；
- 两层判断表；
- PI 内外循环图；
- 生产级结束控制分层图；
- run、turn、model attempt 的嵌套循环图加检查表。

用户对这些版本的核心要求逐渐明确：

- 3.1 说明 LLM 底层停止原因；
- 3.2 说明不同 LLM API 和 adapter 怎样处理；
- 3.3 必须继续上升到 turn 和 run，解释硬限制、错误和用户行为；
- 图要体现包含关系和两个不同循环：同一 turn 内重试 model attempt，以及完成 turn 后进入下一 turn；
- 表格只有在需要对齐多个生产条件时才有价值，不能为了两行内容使用表格。

最终保留的结构是：

1. 从具体 provider 响应建立直觉；
2. 说明 adapter 与真实内容检查；
3. 用 run → turn → model attempt 的范围关系解释继续与结束；
4. 用生产级检查表对齐不同条件、检查时点和结果。

### 可迁移认识

抽象并非越早越好。读者还没有具体经验时，类型定义只会增加新名词。

递进章节必须真的扩大问题范围，而不是使用不同术语重复同一层。

选择图形应服从关系。包含关系应画成嵌套范围，执行顺序才画成流程。

## 6. 模型响应截断：主题边界比“覆盖完整”更重要

### 原方案

截断章节最初同时讨论：

- 普通文本被截断；
- 模型生成的工具调用被截断；
- 工具执行结果过长；
- 大文件分页；
- 命令输出保存；
- MCP 输出限制。

标题使用“最危险的不是少了一段文字”这类新闻式表达，正文还列出较多函数名。

### 用户反驳

用户认为：

- 标题应白描主题；
- 简单逻辑不必引入函数细节；
- “续写”需要解释清楚；
- 通用规则不应放在 Claude Code 小节内部；
- 工具结果过长更属于上下文工程或工具设计，不是 Agent loop 截断章节的重心。

### 最终修改

- 标题改为“模型响应被截断后怎样处理”；
- 只区分普通文本和模型生成的工具调用；
- 说明续写是携带已有文本发起新的模型请求，不是恢复旧网络流；
- 保留 PI 整批作废残缺调用与 Claude Code 有界续写的差异；
- 删除工具结果分页、文件保存和 MCP 输出限制。

### 可迁移认识

一个相关问题不一定属于当前主题。判断标准不是“能不能讲”，而是“它是否帮助回答本节中心问题”。

标题应直接告诉读者这一节处理什么，不用悬念替代主旨。

## 7. Fallback：先说明项目做了什么，再说明没有做什么

### 原方案

Fallback 章节使用函数名、异常类型和内部字段描述 Claude Code 的清理流程。PI 没有自动 fallback 的表述不够准确。工具可能已经执行后的处理又混入了文章推荐方案，读者无法判断源码是否真正实现。

### 用户反驳

用户提出四点：

- 逻辑并不复杂，无需函数级细节；
- PI 到底有没有 fallback；
- 工具副作用难题的解法是项目没实现，还是文章没讲清；
- 标题不要新闻化。

### 最终修改

- 明确 PI 支持跨 provider 历史转换和上层换模型，但核心 loop 不会因失败自动触发 run 级 fallback；
- 用白描说明 Claude Code 怎样作废半成品、补缺失结果、清空旧 attempt 和移除模型绑定信息；
- 按工具未执行、结果可确认、结果不确定三种情况说明边界；
- 明确 Claude Code 实现了状态清理和关闭不安全 fallback，没有提供适用于任意工具的通用副作用恢复。

### 可迁移认识

介绍实现时必须同时说明能力和边界。

来源没有解决的问题，可以提出建议，但必须单独标记，不能用推荐方案填补实现空白。

简单行为优先白描，源码符号只在它们能证明控制顺序或关键边界时出现。

## 8. 流式响应：一节只能有一个主要问题

### 原方案

流式章节同时讲流式原理、UI 更新、提前执行工具、中断恢复和工具进度，读者无法判断章节核心。

### 用户反驳

用户要求先回答：

- 这一节究竟讲流式输出原理，还是中途失败；
- 如果讲原理，能否用具体例子说明数据怎样到达和处理；
- 中断解法是源码实现还是文章补充。

### 最终修改

章节主旨收束为“流式响应怎样进入 Agent loop”，并区分：

- 普通 delta；
- 尚未完成的工具参数；
- 已完整结束的工具块；
- 整条响应完成。

正文用具体事件建立三个完成程度，再对照：

- PI 等完整响应后执行工具；
- Claude Code 可让完整工具块提前进入执行队列。

中断处理按工具尚未启动、排队、执行中和已经完成说明，并明确哪些是源码行为，哪些是工程建议。

### 可迁移认识

章节可以包含多个相关问题，但必须有一个主问题决定顺序和取舍。

解释过程机制时，具体事件序列通常比先列原则更容易建立心智模型。

当两个项目策略不同，分别说明比强行归纳一套统一行为更准确。

## 9. 结构化输出与重试：内容分量要与主题重要性匹配

### 结构化输出

后续审查认为，结构化输出本身只需讲清：

- 合法 JSON 不等于符合 schema；
- 运行时需要再次校验；
- 格式修复应限制次数；
- refusal、截断和 provider error 不能都当成格式错误。

这部分不应因为缺少其他内容而扩写成过长章节。

### 重试

重试章节最初按 PI 和 Claude Code 分别展开，又加入与模型请求重试关系不清的工具副作用设计。用户要求：

- 简单差异可以汇总，不必强制项目对照；
- 先说明什么失败了，再决定重做什么；
- 与本节无直接关系的工具设计不要扩写；
- 解法必须具体，不能只列退避、幂等等名词。

最终正文收束到模型请求错误分类、`Retry-After`、指数退避、随机抖动、次数和总时长，以及工具可能已经执行时停止自动重放。

### 可迁移认识

章节篇幅应由理解难度和主题作用决定，不由文章整体长度决定。

对照不是默认写法。只有差异本身能帮助读者理解时，才分别讲多个项目。

每个专业名词都必须落到“什么条件下采取什么动作”。

## 10. 第 9 节：正确的内容也可能应该删除

### 原方案

第一部分末尾设置“把前面的结论写成可实现的状态机”，包含：

- `LoopPhase`；
- `TerminalReason`；
- `LoopState`；
- 未定义的 `AttemptState`；
- 七步判断伪代码；
- 四条原则。

### 用户质疑

用户认为这一节不知道想表达什么：是总结、升华、实现设计，还是第一部分到面试部分的过渡。

分析后出现过三种选择：

1. 保留并改成生产级实现检查入口；
2. 缩成 PI 与 Claude Code 的共同规则；
3. 删除，让第二部分承担总结和面试转译。

用户先在不同方案间反复比较，最终指出：如果只是归纳，仍然没有必要；若寻找新主题，又会扩展到上下文持久化、可观测性和测试等旁支。

### 最终修改

整个第 9 节删除。第一部分在“模型请求怎样重试”后用一句过渡进入面试部分，并同步调整：

- 开篇的结构预告；
- 第二部分编号；
- 面试追问中的自定义字段；
- 结语对原第 9 节的引用。

### 可迁移认识

文章不需要为了结构完整保留“总结升华”章节。后文已经承担总结功能时，再归纳一次只会重复。

删除章节必须同步检查开篇、过渡、编号、交叉引用和结语。结构修改不是删除一段文本就结束。

## 11. 最终成品保留了什么

当前成品最终保留：

- 从具体故障进入核心问题；这个选择适合该文章复杂的故障链，但不是通用开头；
- run、turn、model attempt 和 tool batch 的基础区分；
- 简化但完整的核心循环图；
- PI 与 Claude Code 的源码对照；
- 从具体 API 到 adapter，再上升到 run 控制的递进；
- 对截断、fallback、流式处理、结构化输出和重试的主题化章节；
- 第三方视角的面试总答和追问；
- 源码 commit、相对路径、关键符号和官方资料；其中相对路径只适合这份本地学习产物，不适合直接发布。

最终删除或否定：

- 把所有生产异常塞入引导状态图；
- 没有证据基础的统一三分类；
- 不属于核心主题的 `suspend`；
- 过多自定义状态类型；
- 工具结果截断等旁支；
- 把推荐方案写成源码能力；
- 新闻式标题和抽象词堆叠；
- 没有独立职责的总结章节。

成品仍然只是一次具体写作结果，不应成为固定模板。可复用的是判断过程。

## 12. Skill 投入使用后暴露出的错误泛化

### 实际结果

Skill 随后用于撰写 `output/agent-context-engineering-and-compaction.md`。新文章再次出现了三个问题：

1. 开头继续使用“假设一个 Coding Agent……”构造复杂场景；
2. 紧接着设置独立的“证据范围”区块，逐条交代源码版本、快照性质和结论分类；
3. 正文把 `../related-repos/...` 等本地路径写成 Markdown 源码链接。

这些问题不是偶然措辞，而是 Skill 中三条规则共同造成的结果。

### 为什么会重复

- 主流程要求记录本地仓库、相对路径、关键符号和 commit，却没有把“内部核实记录”和“正式文章引用”分开；
- 案例把“从具体故障进入核心问题”列为最终保留项，却没有注明这只是原文章的具体选择；
- “具体经验应先于必要抽象”被理解成“开头必须先有一个假设场景”；
- Skill 强调区分事实、推断和建议，却没有说明这种区分应通过自然措辞完成，Agent 因此把内部证据分类直接写成正文声明；
- 终稿检查只验证链接是否存在，没有检查文章发布后读者能否访问。

### 修正后的认识

- 内部研究必须可追溯，正式文章只提供读者能够使用的来源说明；
- 本地源码路径可以保留在内部工作记录，不能作为公开文章链接；
- 事实、推断和建议要在句子中自然归属，不需要“证据范围”或审计式分类区块；
- 开头应选择最短的进入路径，不能把某篇文章有效的故障场景泛化成通用模板；
- 例子只是一种支撑手段，可以出现在最需要建立直觉的章节，不必出现在开头；
- “假设一个……”“想象一下……”“随着……快速发展”“在当今时代”“我们都知道”、连续设问和虚构戏剧场景都不作为作者开头。

### 只在内部建立主线仍然不够

原任务在研究阶段已经有一条内部主线和初步目录，但正式写作前没有把全文主旨、每节职责、读者收益和章节位置完整地放在一起论证，也没有把这份结构提交给用户确认。结果是，很多结构问题直到正文写成后才暴露：停止判断一节多次更换抽象模型和图表，截断与流式章节反复收缩边界，第 9 节最终整节删除。

这些返工不能简单归因于“初稿总要修改”。更直接的原因是，初始大纲主要从研究材料向前展开，没有再从最终结论向后检查：每节是否真的支撑结论，新增认识是否会在后文使用，删除或移动后是否影响全文。用户也只能在看到成文后，逐次指出章节职责和位置不成立。

修正后的做法是：正式写正文前，先确认全文中心问题、主旨、读者起点与终点、内容边界、开头和结尾；再列出每节的具体论点、读者收益、支撑材料、前后关系、当前位置和图表任务。从前往后检查读者是否能逐步理解，再从结论向前检查每节是否必要。只有结构经过双向推演并得到用户认可，才进入正文。

这份大纲是思考和协作工具，不是新的文章模板。源码分析、论文解读和方案分析仍然可以采用完全不同的章节结构；需要固定的是论证过程，而不是章节名称。

这次反馈说明，Skill 不能只保存成功做法，还要写清做法成立的条件。缺少适用条件的经验，很容易在下一篇文章中变成新的机械套路。

## 13. 从整个过程提炼出的写作原则

1. **先确定要让读者理解什么，再决定写哪些内容。** 研究清单不能直接变成目录。
2. **每节必须有独立职责。** 技术正确、资料丰富和篇幅充足都不能替代章节主旨。
3. **抽象结论必须获得具体支撑，但支撑位置由论述需要决定。** API 响应、事件序列、实际行为、数据和例子都能帮助理解；它们不必固定出现在开头。
4. **完整是相对于当前问题完整。** 不要把所有相关异常塞进一节或一张图。
5. **图形类型由关系决定。** 顺序、状态、分支、包含和对照需要不同表达。
6. **图文应当互相增强。** 任何一方都不应只是装饰或补漏。
7. **白描要写出真实动作。** 专业术语保留，空泛抽象改成对象、条件、动作和结果。
8. **来源事实、推断和建议必须自然分开。** 内部证据分类服务于核实，正文通过项目归属和具体措辞表达，不展示证据台账。
9. **结构问题先于措辞问题。** 先决定删、并、移、重写，再润色句子。
10. **敢于删除正确但无用的内容。** 文章价值来自读者形成的认识，不来自覆盖点数量。
11. **发布文章只提供读者能够使用的引用。** 本地路径服务于内部工作，公开文章使用公开链接或自然的文字归属。
12. **开头没有通用模板。** 直接说明问题、结论、概念、事实或取舍通常比编造场景更自然；禁止用套话和戏剧化故障制造注意力。
13. **先确认主旨和章节职责，再写正文。** 从读者起点正向检查理解是否递进，再从最终结论反向检查每节是否必要；未经双向推演的内部主线不足以替代经过确认的大纲。
